# Security notes

netRO is security-sensitive software: it inspects the host, enumerates sockets
and accounts, and can modify firewall rules. This document describes the
controls it implements and the limitations users must understand.

## Threat model

Assets: the host's configuration and firewall state, the integrity baseline,
the log file, and the credibility of netRO's findings.

Adversaries considered:

* Malicious input passed to netRO (targets, ports, paths, config values,
  banners from remote services).
* Local unprivileged users attempting to influence root-run netRO through
  predictable files in `/tmp` or `PATH`.
* Remote services that respond with hostile/oversized data to netRO probes.

## Controls

* **No shell.** Every external program is invoked with an explicit argument
  vector. There is no `sh -c`, `bash -c`, `cmd /c` or string-built command
  line anywhere in the codebase.
* **Target validation.** Hosts are validated for length, characters and
  leading `-` (argument-injection protection) even though arguments are never
  re-parsed by a shell. CIDR prefixes are range-checked. Invalid input returns
  `INVALID_TARGET`.
* **PowerShell without interpolation.** Windows providers pass fixed scripts
  via `-EncodedCommand` (UTF-16LE base64). User-controlled values are validated
  IP literals or paths, never concatenated into script text. `-NoProfile
  -NonInteractive -ExecutionPolicy Bypass` prevents profile-based interference.
* **PATH hardening.** External tools are resolved to absolute paths with
  `which()` and executed by path, so a manipulated `PATH` cannot substitute a
  different binary for a privileged call.
* **Privilege model.** netRO never runs `sudo` on its own. Operations that
  require elevation check the effective privilege first and fail with
  `PERMISSION_DENIED` plus a platform-specific hint. Firewall `--dry-run` works
  unprivileged because it only prints commands.
* **Destructive operations.** `firewall block/unblock` require confirmation
  (interactive) or `--yes` (non-interactive), display every command before and
  after applying, and record rollback information. `unblock` only removes rules
  netRO created and recorded.
* **Files.** The integrity baseline and firewall block state are stored in the
  per-user data directory with `0600` permissions on Unix. Logs are created
  `0600` and rotated at 5 MB. Nothing is written to world-writable `/tmp` with
  predictable names.
* **Logging.** Log values matching `password`, `token`, `secret`, `api_key`
  etc. are redacted before being written.
* **Output escaping.** HTML reports escape every dynamic value; CSV quoting is
  RFC 4180; JSON is generated by `serde_json` (no manual string building).
* **Remote data bounds.** DNS parsing enforces length limits, compression-
  pointer loop detection and bounds checks. Port-scan banners are truncated and
  control characters removed. TLS certificates are parsed defensively.
* **Scan authorization.** Targets that are not loopback/private require the
  explicit `--authorized` flag, and the CLI prints the applicable-use notice.
* **Privacy.** No telemetry, no external HTTP calls at startup or by default.
  Speed tests only contact the server the user configures.

## Known limitations

* Running netRO as root means a compromised external tool (e.g. a trojan
  `nft` or `pfctl`) can do anything root can. netRO cannot defend against a
  compromised system toolchain; verify your packages.
* Integrity monitoring is not malware detection: signatures are hashes of files
  you chose to baseline.
* The built-in TCP tracer cannot report intermediate hop addresses without raw
  ICMP sockets (privileged); it reports hop distance and latency instead.
* SYN ("half-open") scanning is not implemented. The TCP connect scan completes
  handshakes and therefore appears in target logs.
* UDP scanning is inherently ambiguous; results are reported as
  `open|filtered` when no reply arrives.
* Windows provider coverage depends on PowerShell and the CIM cmdlets; when
  they are unavailable, netRO reports `DEPENDENCY_MISSING` rather than
  guessing.
* Findings are configuration evidence, not proof of compromise. A disabled
  firewall can be a deliberate choice; netRO reports it, it does not judge.

## TUI-specific controls

* Remote-derived strings (service banners, TLS certificate fields, DNS answers,
  discovered hostnames/vendors, scan results) pass through
  `util::sanitize_terminal` at the render boundary; ANSI/OSC sequences cannot
  reach a terminal cell. Regression tests inject hostile payloads into tables
  and detail drawers.
* The TUI performs actions through typed values only (`Action`); the command
  palette never builds a command line from user text.
* Destructive actions (firewall block/unblock, snapshot delete) always open a
  confirmation dialog that states the scope ("This machine"; it does not
  disconnect devices from a router).
* Terminal state (raw mode, alternate screen, cursor, mouse capture) is
  restored on exit, on error and on panic.
* The TUI cannot escalate privileges; privileged operations report
  `PERMISSION_REQUIRED` with instructions.

## Reporting a vulnerability

Open a private security advisory on the repository (GitHub → Security →
Advisories) rather than a public issue. Include the netRO version
(`netro version --json`), platform, exact command, and the observed behavior.
